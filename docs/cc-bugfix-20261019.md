# 长春教师培训（col.ccjyxy.cn）死循环排障记录 · 2026-10-19 19:50–20:40

平台口径：`已修 87.8 / 达标 90 学时`（分类0 32.3/30 · 分类1 15.7/15 · 分类2 39.8/45）

## 一句话结论

用户报的"又死循环了"**不是"课里没有视频"**，而是 **点错课 + 记账口径没对齐**。
剩下的 9 门未完成课**全是视频课**，缺口 2.2 学时可以靠自动化补上。

## 四个真因（按危害排序）

### ① 点错课 → 假 done → 认领表堵死（Bug1 + Bug3 的同一个根因）

`cc-lib.openCourse()` 旧写法用 `name.slice(0,16)` 做子串匹配，而平台里**同系列课共享长前缀**：

```
初中数学新课标解读：核心素养的主要表现——抽象能力     ← 已完成（3 段全是「重看」）
初中数学新课标解读：核心素养的主要表现——运算能力     ← 未学习
初中数学新课标解读：核心素养的主要表现——推理能力     ← 未学习   （共 8 门共享前 16 字）
指向核心素养的单元学历案编制——指向核心素养的教学
指向核心素养的单元学历案编制——何为单元学历案？
指向核心素养的单元学历案编制                          （3 门互相包含）
```

`find()` 永远命中列表里**第一门**（多半已完成）→ 进去看到全是「重看」→ `pendingSegs()=0`
→ 被判"无待播段 → 本课结束" → 写 `done:true` 墓碑 → 平台仍显示"未学习"
→ 认领表被假墓碑堵死 → `没有可认领的课（未完成 9 门；已完成标记 9）` 无限循环。

实测证据（19:53）：按**编码**点 C2601759 → 正确打开「运算能力」，3 段全是「播放」，可播。

修：`openCourse(tab,name,log,cat,code)` 有编码按编码点（唯一），进课后**校验页面正文含该编码**；
`enumerate()` 现在带 `code` / `status`；`done` 只由**平台卡片状态「已完成/已学习」**写入，
枚举时并对"平台说未完成却标 done"的墓碑**自动自愈删除**。

### ② 提前 1.5 秒离开播放器 → 那一段永远记不满

服务端 `video-progress/report` 的返回里 `max_position_sec = 历次上报 position 的最大值`。
旧代码 `cur >= dur - 1.5` 就判播完、立刻点「返回课程列表」→ 最后一次上报是 `310.7/311`
→ `max_position_sec` 永远差 0.3 秒 → `completed:false` → 该段无限重进（实测段17/19 各 5s 一轮）。

修：判完阈改为 `dur - 0.2`，且**离开前等 3 秒**让站点发最后一次 checkpoint。
实测：`段1 播完 805.1/805 → 课程页待播段=3（已看完 1）` ✔

### ③ 记账上限 = 1.25 × 该资源累计墙钟 → 播 2x 是纯浪费

抓包两组数据：
```
20:10:20  40s 墙钟 → max_position +50s          （1.25x）
20:09:50 首播起 459s 墙钟 → max_position 564.7  （1.25×459）
```
即**一条 805s 的段，无论倍速多高，最快也只能花 644s 墙钟记满**。
播 2x 时播放器 402s 就冲到末尾，记账只有 62.5% → 必须反复重进补录（每次外加 ~15s 导航开销）。

修：倍速目标从 2x 改为 **1.25x**（改 `cc-lib.HUNTER_JS` 的默认值与 `cc-auto` 的速率守护）。
实测 1.25x 下 `position_sec 384.511 → max_position_sec 384.511`（1:1，不再被削）→ **一趟播完即记满**。
※ 平台 UI 没有 1.25x 档不影响：直接写 `playbackRate`。

### ③b 课级完成有"记账滞后"：全段看完 ≠ 学时到账

实测 C2601738：4 段全部 `completed:true`（最后一段 `586.1/586`），但 `course_completed:false`、
学时 1 小时不动。原因：**课级完成是进课程页那一刻由 `/api/v1/completions/check` 服务端判定的**，
我们播完最后一段 9 秒后回到课程页时，那次 check 早于最后一次 report 落库 → 返回未完成，之后再没人触发。

修：「无待播段」短期跳过 TTL 从 20 分钟缩到 **5 分钟** → 每 5 分钟再进一次课 = 替服务端重跑一次
`completions/check`，直到卡片翻成「已完成」。实测 22:12 复核后补记 **+1.2 学时（89.1 → 90.3，达标）**。
（同理：**不要把"重看最后一段"当常规手段** —— 一次白播 9 分钟；`--replay=1` 只在人工干预时开。）

### ④ 驱动永不退出 → cc-cycle 拿不到轮转时机（Bug2）

旧逻辑只在驱动退出后才重读学时。驱动在某分类里原地打转就永远不切（实测分类1 已 15.7/15 达标还在跑）。

修：
- `cc-auto`：连续 4 次认领不到课 → `exit 0`；连续 25 分钟没播完任何一段 → `exit 0`。
- `cc-cycle`：`runDriver` 内加 2 分钟定时器，**驱动运行中**读 stats 缓存，当前分类达标就 kill 并换分类。

## 顺带修掉的隐患

- `pendingSegs()` 旧写法**不认「重看」**、且 `.MuiListItem-root` 与 `.MuiListItemButton-root`
  嵌套会双计 → 改为 `{pend(播放|继续), watched(重看|重播), total}` 且只取最内层。
- 「无待播段」不再等于完成：只写 `runs/cc-noseg.json`（20 分钟 TTL 短期跳过，语义是"我先躲开"）。
- 服务端 2x 遗留的账差（全「重看」但未完成）→ **补录**：重看最后一段 1–2 次补齐。

## 进程纪律（踩过的坑）

杀进程**不能**用 `-match 'cc-auto\.mjs'`：dsh 的 pwsh 包装进程命令行里只是"引用了"这个文件名，
会被一起杀掉（`runs/` 里那次 4294967295 就是这么来的）。正确写法：

```powershell
Get-CimInstance Win32_Process -Filter "Name='node.exe'" |
  Where-Object { $_.CommandLine -match 'scripts[\\/]cc-auto\.mjs' -and $_.CommandLine -notmatch 'dsh-subprocess-local|runner\.js' }
```

备份：`scripts/cc-{lib,auto,cycle}.mjs.bak-20261019-195452`
